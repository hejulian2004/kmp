# 全局数据埋点通用技术架构规范 (Analytics Technical Architecture Specification)

> **文档性质**：通用技术架构指南（Technical Architecture Guidance）  
> **设计原则**：业务解耦 (Business-Agnostic) | 零依赖启动 (Zero-Dependency Startup) | 强初始化断言 (Strict Initialization Assertions) | 隔离保底 (Fault Isolation & Fallback)  
> **适用范围**：`shared/commonMain` 及跨平台各端入口（Android / iOS / Desktop）

---

## 1. 核心设计原则与架构目标

### 1.1 零依赖最优先初始化原则 (Zero-Dependency Highest Priority Initialization)
- **绝对优先顺序**：埋点单例（`AnalyticsManager`）必须置于应用冷启动统一初始化链的**第 1 步（Step 1）**。
- **零底层依赖**：埋点框架内核绝不依赖网络库（HttpClient）、数据库（SQLite/Room）或业务 Repository，仅依靠内存/标准控制台/纯文件 log 建立基础打点通道。
- **崩溃全捕获**：保证后续网络层初始化失败、数据库坏块崩溃、或动态热更 JSON 抓取失败时，埋点基础设施早已处于就绪状态，能够 100% 捕获并记录故障信息。

### 1.2 强制显式初始化与单例防重约束 (Strict Explicit Initialization & Anti-Duplicate Contract)
- **强初始化断言 (Strict Check Assertions)**：移除静默/隐式默认初始化逻辑。若在调用 `trackEvent()` / `setUserContext()` 等 API 前未执行 `init()`，系统将显式抛出 `IllegalStateException` 提醒开发者，防范遗漏初始化导致的非法状态。
- **单例防重规则 (Anti-Duplicate Check)**：`init()` 内部配置同步校验锁。若已初始化过再次调用 `init()`，系统将主动抛出 `IllegalStateException` 拦截，杜绝多处误重复初始化造成配置覆盖或状态污染。

### 1.3 模块化层级常量结构 (Hierarchical Sub-Object Constant Design)
- **零硬编码字符串**：禁止在代码中硬编码模块标识字符串（如 `"feedline"`、`"instagram"`）或事件名称字符串。
- **子对象层级化划分 (Nested Sub-Objects)**：通过 `AnalyticsModules.<Module>.ID` 与 `AnalyticsModules.<Module>.Events.<Event>` 嵌套子对象组织常量，提升代码可读性、IDE 补全体验与分类归拢度，同时在全局事件中心维护平铺别名（Alias）映射。

### 1.4 异步隔离分发与线程安全 (Asynchronous Fault Isolation & Thread Safety)
- **多渠道 Tracker 隔离**：各个数据通道（Console Tracker / File Log Tracker / Remote HTTP Tracker）互相隔离，单渠道崩溃（如 HTTP 请求超时）绝不影响其他渠道。
- **线程安全锁 (Thread Safety)**：全局属性（`globalParams`）与渠道列表（`trackers`）使用 `synchronized` 保护，防止多协程/多线程并发读写导致异常。
- **零反向影响 (Non-Interfering Failure)**：埋点分发过程中的内部捕获全量容错，绝对不会反向导致主业务 UI 闪退或线程卡死。

## 3. 核心 API 规范与数据格式

### 3.1 基础数据协议 (Common Schema)
上报事件在分发前会自动注入系统通用环境参数：

```json
{
  "event_name": "event_identifier",
  "timestamp": 1785987654321,
  "platform": "Android / iOS / Desktop",
  "app_version": "1.0.0",
  "device_id": "device_uuid",
  "user_id": "user_12345",
  "module_name": "module_id",
  "is_success": true,
  "duration_ms": 120,
  "error_msg": "optional_error_description"
}
```

### 3.2 异常监控与细分报错规范 (Error Tracking Standard)
- **全状态捕获**：所有数据增删改查（CRUD）操作与基础设施初始化事件必须包含 `is_success: Boolean` 结果标志。
- **细分报错 (Sub-Error Reporting)**：当初始化链或子组件失败时，派发统一细分错误事件（如 `INIT_SUB_ERROR`），携带 `sub_module`（如 `network` / `database` / `analytics` / `sdui_prefetch`）与 `error_msg`，实现故障精确排查与定位。

---

## 4. 平台与多语言适配准则 (Multiplatform Guidelines)

- **跨平台适配**：全量代码使用 Kotlin Multiplatform (KMP) `commonMain` 实现，时间戳取自 `Clock.System` 或平台抽象层 `currentTimeMillis()`。
- **并发与协程**：分发通道运行在 `SupervisorJob() + Dispatchers.IO` 独立协程作用域下，确保后台上报不占用主 UI 线程或影响 Compose 120Hz 高刷体验。
