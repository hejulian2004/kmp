# 文件存储架构

> 文档定位：Kotlin Multiplatform 项目文件存储基础设施架构设计  
> 适用范围：`shared` KMP 模块中的 Android / iOS 本地文件存储能力  
> 文档用途：指导后续 Agent 进行代码开发、架构扩展、代码审查、测试与重构  
> 架构级别：Core Infrastructure  
> 当前目标平台：Android、iOS

---

# 1. 文档目标

本文档用于定义项目中的统一文件存储架构。

文件存储能力必须被视为与以下基础设施同级的 Core 能力：

- Network
- Analytics
- Database
- Storage

最终形成：

```text
core/
├── analytics/
├── data/
├── database/
├── init/
├── network/
├── storage/
└── sdui/
```

文件存储层负责统一管理：

- 应用持久文件
- 应用缓存文件
- 临时文件
- JSON 文件
- 图片
- 音视频
- 下载文件
- 上传临时文件
- SDUI 本地快照
- 草稿
- 附件
- 日志文件
- 后续可能增加的离线资源

业务模块不得自行直接实现文件 IO。

本文档的主要目标是：

1. 为 Android / iOS 提供统一文件存储 API。
2. 隔离平台文件系统差异。
3. 隔离 kotlinx-io 等底层库。
4. 防止业务代码直接操作真实文件路径。
5. 提供安全的目录与路径管理。
6. 支持原子写入。
7. 支持并发文件操作。
8. 支持缓存和临时文件管理。
9. 为未来大文件、下载、上传、断点续传等能力提供基础。
10. 保证整个文件存储架构可测试、可维护、可扩展。

---

# 2. 架构原则

整个 Storage 架构必须遵守以下原则。

---

## 2.1 Storage 是 Core Infrastructure

Storage 与 Network、Database、Analytics 同属于基础设施层。

禁止将 Storage 放入：

```text
feature/
repository/
database/
network/
utils/
```

正确位置：

```text
shared/src/commonMain/kotlin/org/example/project/core/storage/
```

Storage 不属于某一个业务模块。

---

## 2.2 业务层禁止直接操作平台文件系统

业务代码禁止直接使用：

```kotlin
java.io.File
Context.filesDir
Context.cacheDir
NSURL
NSFileManager
FileSystem.SYSTEM
```

业务代码也不应直接操作真实绝对路径。

例如禁止：

```kotlin
File("/data/user/0/org.example/files/feedline/data.json")
```

或者：

```kotlin
val path = "/var/mobile/Containers/Data/Application/xxx/Library/..."
```

所有文件操作必须通过：

```text
FileStorage
```

完成。

---

# 3. Storage 与其他数据存储能力的边界

项目中存在多种不同的数据存储机制。

它们必须严格区分。

---

## 3.1 Room Database

Room 用于：

- Feed
- Post
- User
- Message
- Notification
- Entity
- Relation
- Index
- 查询
- 结构化业务数据

例如：

```text
User
Post
Comment
Feed
Notification
```

应放入 Room。

---

## 3.2 SecureStorage

SecureStorage 用于少量敏感数据：

```text
access_token
refresh_token
private key
session credential
```

SecureStorage 不承担普通文件存储功能。

当前：

```text
core/network/auth/SecureStorage
```

仍然继续服务网络鉴权领域。

禁止将以下内容通过 SecureStorage 保存：

```text
图片
视频
JSON
下载文件
日志
SDUI
缓存
附件
```

---

## 3.3 FileStorage

FileStorage 用于：

```text
JSON
文本
图片
视频
音频
下载文件
上传临时文件
附件
SDUI
草稿
缓存
日志
二进制数据
```

---

## 3.4 FileKit

FileKit 负责：

```text
用户选择系统文件
用户导入文件
用户导出文件
系统文件选择器
```

FileKit ≠ FileStorage。

推荐流程：

```text
用户
 │
 ▼
FileKit
 │
 ▼
Import / Export Service
 │
 ▼
FileStorage
 │
 ▼
App Sandbox
```

FileStorage 负责管理应用自己的文件。

FileKit 负责应用与用户文件系统之间的交互。

```text
   │
```

# 6. StorageArea

业务层不得知道真实文件系统目录。

所有文件必须通过逻辑存储区域进行访问。

定义：

```kotlin
enum class StorageArea {

    /**
     * 长期持久数据。
     *
     * 不应该被系统自动清理。
     */
    PERSISTENT,

    /**
     * 可重新生成的数据。
     *
     * 系统允许在磁盘空间不足时清理。
     */
    CACHE,

    /**
     * 生命周期较短的临时文件。
     */
    TEMPORARY
}
```

---

# 7. 平台目录映射

推荐映射关系：

```text
StorageArea.PERSISTENT

Android
    ↓
filesDir

iOS
    ↓
Application Support
```

---

```text
StorageArea.CACHE

Android
    ↓
cacheDir

iOS
    ↓
Library/Caches
```

---

```text
StorageArea.TEMPORARY

Android
    ↓
cacheDir/temp

iOS
    ↓
Temporary Directory
```

业务层不得关心这些平台差异。

---

# 8. StoragePath

禁止 FileStorage API 直接接收任意系统路径。

禁止：

```kotlin
suspend fun read(path: String)
```

推荐：

```kotlin
@JvmInline
value class StoragePath(
    val value: String
)
```

调用：

```kotlin
StoragePath(
    "feedline/images/avatar.jpg"
)
```

这里必须是：

```text
相对路径
```

不得是：

```text
绝对路径
```

---

# 9. 路径安全

StoragePathValidator 必须防止目录穿越和路径逃逸。

禁止以下路径：

```text
../config.json
../../token
/feed/data.json
C:\Users\xxx
foo/../../../secret
```

所有路径必须被限制在：

```text
StorageArea Root
```

以内。

例如：

```text
StorageArea.PERSISTENT
        │
        ▼
Android filesDir
        │
        +
feedline/images/001.jpg
        │
        ▼
filesDir/feedline/images/001.jpg
```

业务层不应存在绕过该规则的 API。

---

# 10. Namespace

为了避免不同 Feature 文件冲突，建议业务层按照 namespace 管理文件。

例如：

```text
persistent/
├── feedline/
├── instagram/
├── airbnb/
├── sdui/
├── profile/
└── common/
```

调用：

```kotlin
StoragePath(
    "feedline/images/001.jpg"
)
```

推荐规则：

```text
<module>/<category>/<file>
```

例如：

```text
feedline/images/avatar.jpg
feedline/drafts/20260811.json

sdui/feedline/layout.json
sdui/instagram/layout.json

profile/avatar/current.jpg

downloads/document/001.pdf
```

不得出现不同模块任意向根目录写文件的情况。

# 11. FileStorage API

第一阶段 FileStorage 公共 API 推荐：

```kotlin
interface FileStorage {

    suspend fun write(
        area: StorageArea,
        path: StoragePath,
        data: ByteArray,
        mode: WriteMode = WriteMode.ATOMIC
    )

    suspend fun read(
        area: StorageArea,
        path: StoragePath
    ): ByteArray

    suspend fun exists(
        area: StorageArea,
        path: StoragePath
    ): Boolean

    suspend fun delete(
        area: StorageArea,
        path: StoragePath
    ): Boolean

    suspend fun metadata(
        area: StorageArea,
        path: StoragePath
    ): StorageMetadata?

    suspend fun list(
        area: StorageArea,
        directory: StoragePath
    ): List<StorageFile>

    suspend fun clear(
        area: StorageArea
    )
}
```

第一版不需要过度加入大量接口。

---

# 12. String 和 JSON

Storage 基础层只需要理解：

```text
ByteArray
```

不要让底层 Storage 与具体 JSON 序列化库高度耦合。

正确：

```text
Domain Object
     │
     ▼
Serialization
     │
     ▼
ByteArray
     │
     ▼
FileStorage
```

而不是：

```text
FileStorage
    │
    ▼
kotlinx.serialization
```

业务 Repository 可以提供：

```kotlin
val jsonString = Json.encodeToString(data)

storage.write(
    StorageArea.PERSISTENT,
    StoragePath("xxx/data.json"),
    jsonString.encodeToByteArray()
)
```

未来如果重复较多，可以在 Storage API 之上增加：

```text
JsonFileStore
TextFileStore
```

但它们属于高级封装。

---

# 13. WriteMode

定义：

```kotlin
enum class WriteMode {

    /**
     * 先写入临时文件，再原子替换目标文件。
     */
    ATOMIC,

    /**
     * 直接覆盖。
     */
    OVERWRITE,

    /**
     * 追加。
     */
    APPEND
}
```

默认必须：

```kotlin
WriteMode.ATOMIC
```

---

# 14. 原子写入

业务重要文件必须使用原子写入。

例如不能：

```text
layout.json

↓

直接覆盖
```

如果 App 在覆盖过程中崩溃：

```text
layout.json

可能只写入了一半
```

推荐：

```text
layout.json.tmp
        │
        ▼
完整写入
        │
        ▼
flush
        │
        ▼
atomic move
        │
        ▼
layout.json
```

适用于：

```text
配置
SDUI JSON
草稿
metadata
离线数据
重要缓存
```

日志类文件可以使用：

```text
APPEND
```

```kotlin
data class StorageMetadata(
```

```kotlin
data class StorageFile(
```

# 17. StorageError

Storage 层必须统一错误模型。

例如：

```kotlin
sealed class StorageError {

    data object NotFound : StorageError()

    data object InvalidPath : StorageError()

    data object PermissionDenied : StorageError()

    data object NoSpaceLeft : StorageError()

    data object AlreadyExists : StorageError()

    data class IoError(
        val message: String?
    ) : StorageError()

    data class Unknown(
        val cause: Throwable
    ) : StorageError()
}
```

是否最终使用：

```text
Result
sealed result
exception
```

可以结合项目统一错误体系决定。

但业务层不得直接依赖平台异常：

```text
IOException
NSException
FileNotFoundException
```

# 18. kotlinx-io 的使用原则

当前项目已经包含：

```text
kotlinx-io
```

因此基础文件系统优先使用 kotlinx-io。

架构要求：

```text
Business
    │
    ▼
FileStorage
    │
    ▼
FileSystemDriver
    │
    ▼
kotlinx-io
```

禁止：

```text
Feature
    ↓
kotlinx-io
```

禁止：

```text
Repository
    ↓
FileSystem.SYSTEM
```

这样未来如果：

```text
kotlinx-io API变化
替换底层文件系统
加入加密文件系统
加入虚拟文件系统
```

只需要修改 Storage Internal。

# 19. FileSystemDriver

推荐增加内部 Driver：

```kotlin
internal interface FileSystemDriver {

    suspend fun write(
        path: String,
        data: ByteArray,
        mode: WriteMode

    suspend fun read(
        path: String
    ): ByteArray

    suspend fun exists(
        path: String
    ): Boolean

    suspend fun delete(
        path: String
    ): Boolean

    suspend fun list(
        path: String
    ): List<String>

```

实际：

```text
DefaultFileStorage
      │
      ▼

      │
      ▼
kotlinx-io
```

同时更容易写 Fake Driver 测试。

# 22. Android 实现

Android 负责将 StorageArea 映射至：

```text
Context.filesDir
Context.cacheDir
```

例如：

```text
PERSISTENT
    ↓
context.filesDir

CACHE
    ↓
context.cacheDir

TEMPORARY
    ↓
context.cacheDir/temp
```

平台 Context 必须使用：

```text
Application Context
```

不得持有 Activity Context。

避免：

```text
Activity Memory Leak
```

# 23. iOS 实现

iOS StorageDirectories 负责将逻辑目录映射到 Sandbox。

推荐：

```text
PERSISTENT
    ↓
Application Support

CACHE
    ↓
Library/Caches

TEMPORARY
    ↓
Temporary
```

iOS 相关 API 只能存在于：

```text
iosMain
```

```kotlin
interface StorageContainer {
```

```kotlin
class DefaultStorageContainer(
```

```kotlin
interface StorageContainer {
```

# 25. AppStorageInitializer

Storage 采用显式初始化。

例如：

```kotlin
object AppStorageInitializer {

    private var _container: StorageContainer? = null

    val container: StorageContainer
        get() = checkNotNull(_container) {
            "Storage 尚未初始化"
        }

    fun init(context: Any?) {

        if (_container != null) {
            return
        }

        val directories =
            createPlatformStorageDirectories(context)

        val storage =
            DefaultFileStorage(
                directories = directories
            )

        _container =
            DefaultStorageContainer(
                fileStorage = storage
            )
    }
}
```

禁止业务代码自行创建：

```kotlin
DefaultFileStorage(...)
```

正常运行时必须从统一 Container 获取。

# 26. AppInitializer

当前 AppInitializer 负责统一初始化项目基础设施。

Storage 加入后推荐初始化顺序：

```text
AppInitializer

1 Analytics

2 Storage

3 Network

4 Database

5 Business Prefetch
```

原因：

Storage 属于低层基础设施。

后续以下能力均可能依赖 Storage：

```text
Network Cache
Log Persistence
SDUI
Download
Upload
Offline Data
```

但注意：

初始化顺序并不代表：

```text
Network → Storage
```

存在架构依赖。

# 28. Repository 的职责

Repository 可以组合多个基础设施。

例如：

```kotlin
class AttachmentRepository(
    private val networkClient: NetworkClient,
    private val storage: FileStorage
)
```

下载：

```text
Repository
    │
    ├── Network 下载
    │
    ▼
ByteArray
    │
    ▼
Storage.write
```

读取：

```text
Repository
    │
    ▼
Storage.read
```

Feature 不关心文件系统。

# 29. Network 与 Storage

Network 不应默认负责磁盘文件。

Network 负责：

```text

Request
Response
Authentication
Retry

```

Storage 负责：

```text
File
Directory
Cache
Disk
```

对于简单下载：

```text
Repository
   │
   ├── Network
   └── Storage
```

# 30. Transfer Layer

如果未来大量出现：

```text

断点下载
断点上传
分片

重试
进度
暂停
恢复
```

则新增：

```text
core/

├── storage/
└── transfer/
```

```text

                ▼          ▼
            Network      Storage
```

```text
任务状态

分片
重试
恢复
checksum
```

Storage 负责磁盘。

# 31. 大文件设计

第一版可以支持 ByteArray API。

但是 Storage 架构必须避免未来被 ByteArray 限死。

例如：

```kotlin
storage.read(...)
```

对于：

```text
5 KB JSON
```

没有问题。

但：

```text
500 MB 视频
```

不应该：

```text
File
 ↓
500MB ByteArray
 ↓
Memory
```

因此未来必须支持：

```text
Source
Sink
Stream
```

或者类似流式 API。

未来接口可能扩展：

```kotlin
suspend fun openSource(...)

suspend fun openSink(...)
```

第一阶段可以不实现。

但代码设计不得阻止未来加入。

---

# 32. 并发模型

文件系统天然存在并发问题。

例如：

```text
Coroutine A
    ↓
write file.json

Coroutine B
    ↓
delete file.json
```

或者：

```text
Coroutine A
    ↓
write

Coroutine B
    ↓
write
```

必须由 Storage 内部统一处理。

业务层不得自行：

```kotlin
Mutex()
```

控制 Storage 并发。

---

# 33. 并发锁粒度

不建议整个 Storage 使用单个全局 Mutex：

```text
Global Mutex

file A write
     ↓
阻塞
     ↓
file B read
```

长期推荐：

```text
Path Based Lock
```

例如：

```text
feed/a.json
    ↓
Lock A

feed/b.json
    ↓
Lock B
```

不同文件可以并行。

同一个文件串行。

第一阶段如果实现复杂，可以暂时采用简单 Mutex。

但必须封装在：

```text
DefaultFileStorage
```

内部。

未来可无感替换。

# 34. IO Dispatcher

所有文件 IO 都不得阻塞 UI 主线程。

Storage 的 suspend API 必须在 IO 场景运行。

例如：

```kotlin
withContext(Dispatchers.IO) {
    ...
}
```

具体 Dispatcher 策略由 Storage 内部负责。

业务层不得每次：

```kotlin
withContext(Dispatchers.IO) {
    storage.write(...)
}
```

Storage API 自己承担执行上下文责任。

# 65. Agent 开发约束

任何 Agent 修改 Storage 架构时必须遵守以下规则。

1. 严格按照本文档定义的职责边界进行开发。
2. 禁止业务模块直接访问底层文件系统。
3. 禁止 Feature 依赖 kotlinx-io。

8. 所有路径必须经过 PathValidator。
9. 默认重要写操作必须使用 ATOMIC。
10. 所有文件 IO 必须避免阻塞主线程。
11. Storage 内部必须负责并发控制。
12. 不得在 Storage 内硬编码业务逻辑。
13. 不得将 SecureStorage 与 FileStorage 合并。
14. 不得将 Room 与 FileStorage 合并。
15. 所有新代码必须有对应测试。
16. 关键函数与文件必须使用中文注释。
17. 硬编码字符串必须根据职责统一抽取。
18. 文件和目录结构发生变化时必须同步修改本文档。
19. 如果实现过程中发现本文档架构无法满足需求，应先更新架构设计，再继续编码。
20. 不允许为了快速完成任务绕过现有架构。

```text
业务操作真实磁盘
```

业务只知道：

```text
StorageArea
StoragePath
FileStorage
```

底层负责：

```text
Platform Directory
Path Resolution
Path Validation
Concurrency
Atomic Write
kotlinx-io
Error Mapping
File System
```

最终调用链：

```text
Feature
   │
   ▼
Repository
   │
   ▼
FileStorage
   │
   ▼
DefaultFileStorage
   │
   ├── PathValidator
   ├── PathResolver
   ├── Concurrency Control
   └── FileSystemDriver
              │
              ▼
          kotlinx-io
              │
       ┌──────┴───────┐
       ▼              ▼
    Android          iOS
```

Storage 应作为整个 KMP 项目的长期基础设施，而不是一个 FileUtils 工具集合。

后续所有：

```text
SDUI 本地缓存
图片缓存
离线资源
草稿
附件
网络下载
上传临时文件
日志落盘
大文件
断点传输
```

均应建立在这一基础架构之上。

任何后续 Agent 在新增文件相关能力前，都必须首先判断：

```text
这是文件系统基础能力？

→ core/storage

这是缓存淘汰策略？

→ storage/cache

这是文件上传下载任务？

→ core/transfer

这是业务数据？

→ Repository / Feature

这是结构化数据？

→ Room

这是敏感凭证？

→ SecureStorage

这是用户导入/导出？

→ FileKit
```

通过这一职责划分保持项目长期可维护性。
