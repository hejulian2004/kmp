# KMP 本地优先数据同步与离线策略规范

> **文档版本**：4.0  
> **更新日期**：2026-08-05  
> **适用范围**：Repository 实施、本地数据库 (Room / SQLDelight)、缓存策略、读写分流、离线 Outbox 队列  
> **核心原则**：Local-First, Single Source of Truth (SSOT), Read/Write Separation (读写分流), Stale-While-Revalidate (SWR), Atomic Transaction, Field-Level Rollback

---

## 1. 核心约束与结果语义

### 1.1 读写分流架构规范 (Read/Write Separation)
- **读路径（Query / Data Sync）**：全量模块统一使用项目全局 `networkBoundResource` 管道与 `ResourceState<T>` 状态模型。强制执行 **SWR (Stale-While-Revalidate)** 流程：优先使用内存/数据库缓存 0ms 渲染 UI ➔ 异步发起网络同步 ➔ 网络成功更新数据库 ➔ 数据库响应式 Flow 触发 UI 刷新；网络失败优雅保留本地缓存降级展示。
- **写路径（Mutation / Write）**：全量写请求统一使用 `AppResult<T>` + 离线 Outbox 队列事务，执行乐观更新与字段级回滚。

### 1.2 读路径资源状态模型 (`ResourceState<T>`)
```kotlin
sealed interface ResourceState<out T> {
    /** 加载中（带旧缓存数据，供 UI 0ms 瞬间渲染） */
    data class Loading<T>(val cachedData: T? = null) : ResourceState<T>

    /** 数据同步成功，返回最新权威数据 */
    data class Success<T>(val data: T) : ResourceState<T>

    /** 网络同步失败（带旧缓存降级数据 + 领域错误 AppError，保证离线可用不崩溃） */
    data class Error<T>(val error: AppError, val cachedData: T? = null) : ResourceState<T>
}
```

### 1.3 读路径通用同步管道 (`networkBoundResource`)
```kotlin
inline fun <Key, Entity, NetworkDto> networkBoundResource(
    key: Key,
    crossinline queryLocal: (Key) -> Flow<Entity?>,
    crossinline fetchRemote: suspend (Key) -> NetworkDto,
    crossinline saveRemoteResult: suspend (Key, NetworkDto) -> Unit,
    crossinline shouldFetch: (Entity?) -> Boolean = { true }
): Flow<ResourceState<Entity>>
```

### 1.4 写路径约束与结果语义
- **必须**：本地数据库 / `LocalDataSource` 是 UI 观察数据的唯一可信来源 (SSOT)。
- **必须**：旧字段读取、乐观状态更新与 `PendingMutation` 插入必须在**同一个数据库事务**中完成。
- **必须**：Repository 函数契约统一使用带异步状态的 `AppResult`：
  ```kotlin
  sealed interface AppResult<out T> {
      data class Success<T>(val data: T) : AppResult<T>
      data object PendingSync : AppResult<Nothing> // 本地写入成功，已放入 Outbox 排队异步同步
      data class Failure(val error: AppError) : AppResult<Nothing> // 终态错误或无效请求
  }
  ```
- **必须**：并发与冲突控制采用明确分工：
  - `MutationSequencer`：保证同一实体的写请求在内存/队列中串行发送。
  - `operationId`：只处理当前客户端的响应乱序。
  - `idempotencyKey`：仅用于保证请求在网络重试时被服务端**防重执行**。
  - `serverVersion` / `ETag` / 服务端 Last-Write-Wins 规则：处理**多设备并发修改**冲突。
- **禁止**：禁止在 ViewModel 或 UI 层生成 `operationId`。`operationId` 必须由 Repository / `MutationCoordinator` 内部生成。
- **必须**：结果处理与 Outbox 更新必须在**各自对应的同一数据库事务**中完成，严禁拆分：
  - `confirmIfCurrent`：实体标记 `Synced` + Outbox 标记 `Succeeded`；
  - `rollbackIfCurrent`：实体字段回滚 + Outbox 标记 `Cancelled`；
  - `scheduleRetryIfCurrent`：实体保持 `Pending` + Outbox 标记 `RetryScheduled`；
  - `markReconcileRequiredIfCurrent`：实体保持 `Pending` + Outbox 标记 `ReconcileRequired` (结果不确定，需复用 `idempotencyKey` 对齐权威状态)；
  - `markFailedIfCurrent`：实体标记 `Failed` + Outbox 标记 `NeedsUserAction`。

## 2. 状态模型

### 2.1 本地实体状态 (`SyncState`)
```kotlin
enum class SyncState { Synced, Pending, Failed }
```

### 2.2 Outbox 任务状态 (`MutationStatus`)
```kotlin
enum class MutationStatus {
    Pending,           // 排队等待发送
    InFlight,          // 请求发送中 (加租约锁)
    RetryScheduled,    // 确定未发送/临时失败，已安排下一次退避重试
    ReconcileRequired, // 结果不确定 (如 Timeout/连接中断)，需复用原 idempotencyKey 重试或查权威状态
    Succeeded,         // 确认成功
    NeedsUserAction,   // 遇到终态错误 (400/403)，终止自动重试，等待用户处理
    Cancelled          // 被新的用户操作覆盖取消
}
```

### 2.3 Outbox 任务模型 (`PendingMutation`)
```kotlin
data class PendingMutation(
    val operationId: String,
    val entityType: String,
    val entityId: String,
    val operationType: String,
    val idempotencyKey: String,        // 默认等于 operationId
    val payload: String,
    val payloadVersion: Int,
    val rollbackPayload: String?,      // 持久化回滚快照 JSON (仅在确定未发送时用于安全回滚)
    val status: MutationStatus,
    val attemptCount: Int,
    val leaseExpiresAtMillis: Long?,   // InFlight 租约到期时间戳 (防僵尸锁)
    val nextAttemptAtMillis: Long?,
    val lastErrorCode: String?,
    val createdAtMillis: Long,
)
```

## 3. 请求确定性与写操作事务

### 3.1 请求确定性契约 (`RequestOutcome`)
```kotlin
enum class RequestOutcome {
    NotSent,    // 确未发送：请求构建失败、发送前确认离线 → 允许 RollbackAndCancel 或 RetryScheduled
    Rejected,   // 明确拒绝：400, 401, 403, 409, 412 等服务端明确错误 → 映射 NeedsUserAction / Rollback
    Unknown     // 结果不确定：Timeout, 连接重置, 响应丢失, 写请求 5xx → 严禁直接回滚，必须置为 ReconcileRequired
}
```

### 3.2 单事务原子规范
> **强制规范**：
> 1. 准备阶段：读取旧字段、写入乐观状态、持久化 `rollbackPayload` 与插入 Outbox 必须在同一个数据库事务中完成。
> 2. 确认阶段：`confirmIfCurrent` 必须在同一个数据库事务中更新实体状态为 `Synced` 并将 Outbox 状态更新为 `Succeeded`。
> 3. 回滚/重试/对齐/失败阶段：根据 `RequestOutcome` 确定性选择对应接口，必须在同一个数据库事务中完成实体状态更新与 Outbox 状态变更。

### 3.3 条件更新与回滚接口规范
```kotlin
interface ConditionalMutationStore<ServerPatch, RollbackPatch> {
    // 成功确认：实体 Synced + Outbox Succeeded
    suspend fun confirmIfCurrent(entityId: String, operationId: String, patch: ServerPatch): Boolean

    // 确定未发送/明确可回滚失败：实体字段回滚 + Outbox Cancelled
    suspend fun rollbackIfCurrent(entityId: String, operationId: String, patch: RollbackPatch): Boolean

    // 确定未发送之临时网络失败：实体保持 Pending + Outbox RetryScheduled
    suspend fun scheduleRetryIfCurrent(entityId: String, operationId: String, nextAttemptAtMillis: Long, errorCode: String?): Boolean

    // 请求结果不确定 (Timeout/网络中断/写请求 5xx)：实体保持 Pending + Outbox ReconcileRequired (复用 idempotencyKey 重试或查权威状态)
    suspend fun markReconcileRequiredIfCurrent(entityId: String, operationId: String, nextAttemptAtMillis: Long, errorCode: String?): Boolean

    // 终态业务失败：实体 Failed + Outbox NeedsUserAction
    suspend fun markFailedIfCurrent(entityId: String, operationId: String, errorCode: String?): Boolean
}
```

## 4. 失败策略与启动恢复规则

三类失败策略**必须按操作类型选择，禁止在同一次 Mutation 中混用**。

```kotlin
enum class MutationFailurePolicy {
    RollbackAndCancel,        // 状态型操作：确定未发送失败时回滚本地并取消 Outbox
    KeepPendingAndRetry,      // 内容型操作：保留 Pending，Outbox 标记退避重试
    KeepFailedForUserAction   // 终态错误：标记 NeedsUserAction / Failed，等待用户处理
}
```

### 4.1 策略与启动恢复对照表

| 场景 / 错误类型 | 请求确定性 (`RequestOutcome`) | 处理策略 | Outbox 状态 | 实体状态 | 恢复 / 处理动作 |
|---|---|---|---|---|---|
| **发送前确认离线** | `NotSent` (确未发送) | `RollbackAndCancel` | `Cancelled` | 字段级回滚 | 立即回滚并提示 |
| **400 / 403 业务错** | `Rejected` (已被拒绝) | `KeepFailedForUserAction` | `NeedsUserAction` | `Failed` | 停止自动重试，等待用户手动修改 |
| **Timeout / 连接中断** | `Unknown` (**结果不确定**) | 保持 Pending 协商 | `ReconcileRequired` | `Pending` | **严禁直接回滚**。复用原 `idempotencyKey` 重试或查询权威状态 |
| **`InFlight` 租约超时** | `Unknown` (**结果不确定**) | 统一转对齐 | `ReconcileRequired` | `Pending` | **严禁直接回滚**。自动恢复为 `ReconcileRequired` 并设置 `nextAttemptAtMillis` 重试 |
| **进程重启 (Unsent)** | `NotSent` (确认未发送) | `RollbackAndCancel` | `Cancelled` | 字段级回滚 | 读取 `rollbackPayload` 原子回滚实体，**不得重新发送** |

## 5. Outbox 原子领取与防僵尸锁调度

### 5.1 原子领取 (Atomic Claim)
消费者获取任务时，必须通过条件更新原子地将任务从 `Pending/RetryScheduled/ReconcileRequired` 改为 `InFlight`，且**必须校验到期时间**：

```sql
UPDATE pending_mutation
SET 
    status = 'InFlight',
    lease_expires_at_millis = :leaseExpiresAtMillis
WHERE 
    operation_id = :operationId
    AND (
        status = 'Pending'
        OR (
            status IN ('RetryScheduled', 'ReconcileRequired')
            AND next_attempt_at_millis <= :currentTimeMillis
        )
    );
```

### 5.2 租约与过期恢复 (Lease Recovery)
- **租约设置**：每次领取设 30~60 秒的 `leaseExpiresAtMillis` 租约。
- **租约超时恢复**：在应用启动或轮询扫表时，对于状态为 `InFlight` 且 `leaseExpiresAtMillis < currentTimeMillis()` 的过期僵尸任务，**因其请求结果不确定 (Unknown)，统一恢复为 `ReconcileRequired` 状态**并设置 `nextAttemptAtMillis`，严禁直接回滚。

### 5.3 触发源
1. 变动写入完成时。
2. 应用启动与回到前台。
3. 网络连接恢复提示。
4. 前一个任务成功后自动消费下一个。
5. Android WorkManager / iOS BGTaskScheduler 后台调度触发。

## 6. 冲突处理与安全

- **冲突解决**：多设备并发修改通过 `serverVersion`、`ETag` 或服务端明确的 Last-Write-Wins 规则处理；`idempotencyKey` 仅用于避免同一操作在网络重试时被重复执行。服务端返回 `409 Conflict` 或 `412 Precondition Failed` 时，客户端统一映射为 `NetworkError.Conflict` 并回滚。
- **载荷安全**：Outbox `payload` 与 `rollbackPayload` 严禁包含 Token、密码或长期凭据；敏感载荷需本地加密存储。

## 8. 图片与多媒体多级离线缓存体系

为配合 Local-First 离线优先体验，多媒体资源（用户动态配图、视频封面、用户头像与网络大图）实行统一的多级缓存与持久化策略：

### 8.1 媒体发布持久化链路
- **相册临时 URI 隔离**：针对 Android / iOS 系统选择器返回的临时 `content://` URI，在发布阶段由 `MediaPersister` 立即通过 `FileStorage.write(StorageArea.PERSISTENT, ...)` 转存为沙盒内部物理文件。
- **本地绝对物理路径入库**：SQLite 数据库只存储受信任的内部物理路径，确保应用冷启动、杀进程或离线脱机时 100% 可正常加载展示。

### 8.2 网络图片与头像三级离线缓存
- **L1 内存缓存**：Coil 3 `MemoryCache` 动态分配 25% 堆内存，实现列表高频滚动 0ms 命中。
- **L2 磁盘缓存**：挂载 `StorageArea.CACHE` 下 256MB 物理文件池 (`image_cache`)，断网离线时自动降级读取本地磁盘文件。
- **L3 网络同步**：通过 Ktor 引擎异步拉取，根据 HTTP 响应头自动同步并更新 L2 磁盘缓存。

### 8.3 网络视频流式预加载与磁盘离线缓存 (`AppVideoCacheManager`)
- **播放拦截**：`VideoPlayer` 加载网络视频时自动映射本地沙盒 `StorageArea.CACHE/video_cache/`，命中时零延迟本地起播；
- **异步预热**：未命中时在首播的同时触发后台静默预下载，全量写入 512MB 磁盘缓存池；
- **离线脱机支持**：已缓存视频在无网络/弱网环境下依然可离线反复流畅播放。
